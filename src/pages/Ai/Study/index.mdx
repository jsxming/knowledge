# AI 编程团队落地指南

> **核心命题**：AI 编程的威力不在个人技巧，而在于团队能否把「提示词规范 + 团队工作流 + 工程化保障」组织成一套可复制的体系。
> 本文从实际使用中的问题出发，围绕「AI 编程如何在一个团队中真正落地」展开，共分为六个部分：

1. **落地过程中遇到的实际问题** — 认清阻力，才能对症下药
2. **第一块基石：写好 Prompt 与 CLAUDE.md** — 让 AI 一次做对
3. **第二块基石：定义团队工作流（SDD）** — 让产出稳定可控
4. **第三块基石：工程化保障** — 让 AI 代码安全合并
5. **团队落地路线图** — 从个人工具到团队生产力的三个阶段
6. **效果衡量与持续迭代** — 用数据驱动优化

---

## 一、落地过程中遇到的实际问题

团队引入 AI 编程，最先面对的不是技术问题，而是**期望、习惯与流程的错位**。以下问题在大多数团队中反复出现：

### 1.1 期望错位：把 AI 当作「全知全能的资深架构师」

直接输入「帮我写一个电商网站」，然后拿着 AI 生成的「玩具代码」直接上线，导致安全漏洞百出或根本无法运行。

> **对策**：AI 是**高效的程序员助理**，不是免费的架构师。业务架构、技术选型、风险决策永远由人来拍板；AI 负责把它拆成可执行的编码任务并高质量执行。

### 1.2 代码水土不服：与项目规范完全不兼容

AI 生成的代码虽然语法正确，但现有项目的风格（如 ESLint 规则）、目录结构（如 `@/utils` 别名）、状态管理（如 Redux / Zustand）完全不搭，强行粘贴后项目直接报红。

> **对策**：把项目规范写进 `CLAUDE.md`（见第二章），让 AI 在动手前就「入乡随俗」，从源头消除风格偏差，而不是事后手工返工。

### 1.3 成本失控：token 消耗过快

长对话、反复试错、每次重跑上下文，都会快速烧掉预算。没有成本意识的团队，一个季度下来 token 账单往往远超预期。

> **对策**：用「分步确认」控制上下文长度（见 2.2）；把高频重复任务沉淀为 skill / 脚本；按任务类型选用不同档位的模型，而非一律用最强的。

### 1.4 上下文断裂：AI 没有记忆

类似的问题，窗口关闭后又要跟它再描述一遍。每个会话都是「失忆的实习生」，团队积累的经验无法跨会话复用。

> **对策**：把团队上下文沉淀到项目级 `CLAUDE.md`；关键决策、代码约定记录成文档，让每次新会话都站在团队已有的认知起点上。

### 1.5 质量审查困难（高频痛点）

AI 生成的代码「看起来都对」，但审查者难以快速发现深层缺陷——AI 代码的平均缺陷率与人类相当，只是**错误类型不同**：人类容易遗漏边界，AI 容易犯逻辑看似自洽、实则与业务语义不符的错误。

> **对策**：AI 代码必须走与人类代码完全相同的审查流程，且审查重点应放在**业务语义与边界条件**上，而非语法风格（见第四章）。

### 1.6 安全与合规风险

公司代码外发给第三方模型、生成代码引入已知漏洞（依赖版本陈旧、不安全的加密方式）、以及 AI 幻觉出的不存在依赖包（依赖投毒风险）。

> **对策**：敏感项目使用私有化部署或合规模型；依赖锁定版本并定期扫描；生成代码上线前过安全检测。

### 1.7 技能退化焦虑

团队过度依赖 AI，遇到 AI 不擅长的领域（老旧框架、复杂并发）时反而无从下手。

> **对策**：把 AI 定位为「辅助而非替代」——核心模块、复杂逻辑保持人工主导，AI 用于提速重复劳动与探索性验证。

### 1.8 问题与对策一览

| 问题维度 | 典型症状 | 对应解法 | 章节 |
| --- | --- | --- | --- |
| 期望错位 | 「帮我写个电商网站」直接上线 | 人拍板架构，AI 执行编码 | 第一章 |
| 代码不兼容 | 粘贴后项目报红 | 规范写入 CLAUDE.md | 第二章 |
| 成本失控 | token 账单超预期 | 分步确认 + 沉淀 skill | 2.2 / 4.5 |
| 上下文断裂 | 每次重新描述需求 | 项目级 CLAUDE.md | 2.3 |
| 审查困难 | 代码看着对但不敢合 | 审查闸门 + 测试兜底 | 第四章 |
| 安全合规 | 代码外泄 / 依赖投毒 | 合规模型 + 依赖锁定 | 第四章 |
| 技能退化 | 离开 AI 不会写代码 | 核心逻辑人工主导 | 第四章 |

## 二、第一块基石：写好 Prompt 与 CLAUDE.md

> 同样的任务，为什么有人能让 Claude 一次就给出完美答案，我却要来回改好几遍？
> 答案通常不在于 AI 的能力差异，而在于**指令的质量**。优秀的指令如同一份完美的需求文档：清晰、具体、无歧义。

### 2.1 精准表达技巧

#### ① 量化一切

避免模糊描述，务必使用具体数据：

| 模糊描述 | 精准描述 |
| --- | --- |
| 处理大量数据 | 处理 100 万条记录 |
| 响应要快 | P99 响应时间小于 200 ms |
| 代码要简洁 | 函数不超过 20 行，参数不超过 4 个 |
| 做好用户体验 | 首屏加载时间小于 2 秒，操作步骤不超过 3 步 |

#### ② 示例驱动

对于复杂需求，一个示例胜过 10 句描述：

```js
需求：将驼峰命名转换为蛇形命名

示例：
输入： "getUserName" → 输出： "get_user_name"
输入： "HTTPRequest" → 输出： "http_request"
```

#### ③ 明确边界

定义「禁止项」与定义「执行项」同等重要，要防止 AI 越界：

- **范围限制**：仅修改 auth 模块，严禁触碰其他文件。
- **工具约束**：必须使用项目现有的 logger，禁止使用 `console.log`。
- **依赖管理**：严禁添加任何新依赖。
- **失败处理**：若遇到无法解决的问题，请立即报告并停止操作，切勿反复尝试。

#### ④ 一次只做一件事

把「重构并加新功能并修 bug」拆成三个独立会话。单一职责的指令，输出质量显著高于多目标混合指令。

### 2.2 分步确认：把大任务拆成验证闭环

针对复杂任务，分步执行远胜于一次性提交。通过将大需求拆解为独立的验证闭环，可显著降低偏差风险：

```js
第一步："请分析这个 bug 的根本原因，暂不修改代码。"
（待确认分析逻辑正确后，进入第二步）

第二步："基于上述分析修复 bug，仅修改必要代码。"
（待确认修复方案无误后，进入第三步）

第三步："为此次修复编写对应的测试用例。"
```

这种模式的好处是**每一步均可独立验证**，防止 AI 在错误方向上过度执行，同时也把 token 消耗控制在可预期的范围内。

### 2.3 CLAUDE.md：团队的「项目记忆」

`CLAUDE.md` 是 AI 每次会话开始时必读的上下文文件，相当于项目的**入职手册**——新人（AI）靠它快速了解项目，而不是每次都重新问一遍。

#### 三层结构

| 层级 | 位置 | 作用 | 示例内容 |
| --- | --- | --- | --- |
| 组织级 | `~/.claude/CLAUDE.md` | 个人 / 团队统一规范 | 代码风格偏好、常用命令、常用工具链 |
| 项目级 | `<仓库根>/CLAUDE.md` | 当前项目专属上下文 | 技术栈、目录结构、路由约定、数据层规范 |
| 用户级 | `~/.claude/CLAUDE.local.md` | 个人习惯（不入库） | 个人常用别名、忽略规则 |

#### 项目级 CLAUDE.md 应包含什么

- **常用命令**：启动、构建、测试、lint 的准确命令
- **技术栈与版本**：框架、UI 库、状态管理、构建工具
- **目录结构与导入约定**：如路径别名 `@` → `src/`、组件目录规范
- **数据与状态约定**：数据持久化方案、关键 key 前缀
- **风格红线**：ESLint 规则、禁止事项（如禁止内联样式）
- **常见坑**：团队踩过的坑与规避方式，防止 AI 重复踩

#### 示例模板

```md
# 项目说明

此文件用于指导 AI 在该仓库中进行代码开发。

## 常用命令
yarn dev        # 启动开发服务器
yarn build      # 类型检查 + 生产构建
yarn lint       # 运行 oxlint

## 技术栈
- 框架：React 19 + TypeScript + Vite
- UI 库：Ant Design 6
- 路由：React Router DOM v7，嵌套 <Outlet /> 布局
- 状态：全部持久化到 localStorage，键前缀为 knowledge_app_

## 目录结构
src/
├── components/   # 共享 UI 组件，采用 组件名/index.tsx 结构
├── pages/        # 路由级页面
├── constants/    # 常量定义
└── utils/        # 工具函数

## 注意事项
- 导入一律使用 @/ 路径别名
- 禁止使用内联样式（style={{...}}），使用 Less 模块
```

> **团队维护约定**：CLAUDE.md 不是一次性文档——每次代码审查、每次架构调整后，顺手同步更新，它才能真正成为团队的「活记忆」。

## 三、第二块基石：定义团队工作流（SDD 规范驱动开发）

> 团队要做的，就是定义适合当前团队开发风格的工作流。

如何将分散的组件（skill、hooks、MCP、plugins）串联成一套完整的工作流？AI 时代的软件工程方法论应当是何种形态？GitHub 上涌现出大量基于 Claude Code（或其他 AI）的插件与框架，它们都在尝试回答这个命题，尽管路径各异，答案却殊途同归：

**即 SDD（Specification-Driven Development，规范驱动开发）：先定义规范，再编写代码。**

SDD 的核心不在于依赖何种插件，而在于确立**「先思后行」的开发习惯**。如果能在启动 AI 之前，仅用 5 分钟理清「目标范畴（做什么、不做什么）」与「验证标准」，即使不安装任何插件，其成效也已超越 90% 的凭感觉编程（如 Vibe Coding）。插件的本质，仅是将这一关键习惯自动化而已。

### 3.1 一个可落地的 SDD 工作流

```text
需求澄清 → 规范定义 → 计划拆分 → 逐步实现 → 独立验证 → 代码审查 → 合并交付
```

| 环节 | 人的职责 | AI 的职责 | 产出物 |
| --- | --- | --- | --- |
| 需求澄清 | 明确做什么、不做什么 | 提问澄清歧义、列出假设 | 需求清单 |
| 规范定义 | 拍板边界与验收标准 | 起草规范草案、给出风险点 | 规范文档 / 计划 |
| 计划拆分 | 确认拆分粒度 | 拆解为可独立验证的子任务 | 任务清单 |
| 逐步实现 | 每步确认后再放行 | 实现单个子任务 | 代码 + 自测 |
| 独立验证 | 运行测试、人工抽查 | 补充测试用例、自查 | 通过的测试 |
| 代码审查 | 逐行 review、把关 | 说明变更动机、回应评论 | 审查记录 |
| 合并交付 | 决定是否合并发布 | 生成提交信息、更新文档 | 合并的 PR |

### 3.2 两个关键认知

> 「工程化」的核心要义：让强大却充满不确定性的工具，在秩序井然的系统中**可靠地创造价值**。

> Harness 工程的本质：并非编程行为，而是**约束行为**。

## 四、第三块基石：工程化保障

Prompt 和工作流解决「AI 是否做对」的问题；工程化保障解决「AI 做错了会不会进生产线」的问题。

### 4.1 代码审查闸门：AI 代码必须被审查

AI 生成的代码与人类代码走**同一条审查流程**，不设绿色通道。审查时重点关注：

- **业务语义**：AI 是否误解了需求（最常见的错误）
- **边界条件**：空值、超时、并发、异常分支
- **隐藏依赖**：是否有幻觉出的包、魔法数字、硬编码
- **安全红线**：鉴权、注入、敏感信息泄漏

> 可以要求 AI 在提交 PR 时**主动说明**：改了什么、为什么这么改、自测了什么、可能的风险点——这能把审查成本降低一半以上。

### 4.2 测试兜底：先写测试，再写实现

让 AI 遵循 TDD（测试驱动开发）模式：

```js
第一步："根据这个需求，先写测试用例（含边界条件）。"
（待确认测试覆盖需求后，进入第二步）

第二步："实现代码，使测试全部通过，禁止为了通过测试而篡改测试。"
```

测试是 AI 代码的**安全网**——有了它，CI 才能兜底，审查者才能放心合并，后续重构才有底气。

### 4.3 提交与文档规范

- **提交信息**：让 AI 生成符合团队规范的 commit message（如 Conventional Commits），杜绝「fix bug」「update」这类无意义提交。
- **PR 描述**：自动生成变更摘要、影响范围、测试说明。
- **文档同步**：接口变更、配置变更，要求 AI 同步更新对应文档，避免「文档与代码脱节」。

### 4.4 渐进式授权

按风险等级逐步放开 AI 的权限，而不是一开始就全自动：

| 阶段 | 模式 | 适用场景 |
| --- | --- | --- |
| 第一阶段 | 建议模式（只给方案，不动代码） | 新人 / 高风险模块 |
| 第二阶段 | 计划模式（先出计划，人确认后执行） | 常规功能开发 |
| 第三阶段 | 自动模式（直接执行，走审查闸门） | 低风险、高重复任务 |

敏感操作（生产环境、删除数据、发布上线）始终需要**人工确认**，无论处于哪个阶段。

### 4.5 沉淀团队资产

把高频任务固化下来，让团队的 AI 能力持续复利：

- **skill**：项目专属的最佳实践（如「按本项目规范创建组件」）
- **CLAUDE.md**：团队上下文（见 2.3）
- **脚本与模板**：重复的脚手架、代码生成、提交动作
- **知识库**：踩坑记录、决策记录，供 AI 检索参考

> 判断标准：一件事在团队里做超过三次，就应该沉淀为资产。

## 五、团队落地路线图

从「个人用着爽」到「团队生产力」，建议分三个阶段推进：

### 阶段一：试点（约 2-4 周）

- **目标**：跑通一条完整的 AI 辅助开发流程，收集真实数据
- **动作**：选择 2-4 人的先锋小队；选定一个中等复杂度项目；先行沉淀 CLAUDE.md；用 SDD 流程完成 3-5 个真实需求
- **验证标准**：流程顺畅度、开发者真实感受、token 成本符合预期

### 阶段二：推广（约 4-8 周）

- **目标**：从试点团队扩散到全组，规范成型
- **动作**：根据试点反馈修订工作流；补充工程化保障（审查闸门、测试兜底）；设立 skill / 模板资产库；组织内部培训与分享
- **验证标准**：多数成员每周稳定使用；AI 产出代码可合并率明显提升

### 阶段三：制度化（持续）

- **目标**：AI 编程融入日常研发流程，成为默认方式
- **动作**：纳入团队开发规范文档；明确「AI 平台工程师」角色（负责维护 CLAUDE.md、skill、模型配置）；按月复盘指标、持续优化
- **验证标准**：新成员入职后一周内即可上手 AI 辅助开发

### 落地自检清单

- [ ] 项目级 CLAUDE.md 已编写并纳入代码审查
- [ ] 团队达成一致的 Prompt 规范（量化 / 示例 / 边界）
- [ ] SDD 工作流文档化，人人知晓
- [ ] AI 代码与人类代码走同一条审查流程
- [ ] 核心项目已接入测试兜底与 CI
- [ ] 敏感操作已配置人工确认
- [ ] 高频任务已沉淀为 skill / 模板
- [ ] 已确定成本预算与模型分级策略

## 总结

AI 编程的团队落地，本质上是**三件事的工程化**：

1. **输入侧**：把需求写成 AI 一次就能做对的指令（Prompt + CLAUDE.md）
2. **过程侧**：用规范驱动的工作流约束不确定性（SDD）
3. **输出侧**：用审查与测试守住质量底线（工程化保障）

> AI 会越来越强，但**工程纪律**不会自己发生——它需要团队有意识地去建立。率先把这三件事做成体系的团队，会拿到 AI 时代最大的红利：同样的团队规模，数倍的交付能力。
